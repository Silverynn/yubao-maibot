# 协作与交接

## 每次开始前

1. 查看 GitHub 任务、PR 和队友交接，确认是否正在改同一模块。
2. 外层执行 `git status`；MaiBot 和对应插件目录也分别执行 `git status`。
3. 有未提交修改先保存并核对，再同步主分支。不要用 reset --hard、整目录覆盖或清库解决同步问题。
4. 新建自己的功能分支，例如 `git switch -c feature/memory-observation`。

## 每次交付

PR 至少写：问题／修改后的行为／改动入口／如何验证／已知限制／是否影响配置或启动补丁。附可复现的虚构测试输入，不附私人群聊数据。

一次只处理一个小目标，代码和原理笔记一起交付。两人的 Codex 不共享聊天上下文，事实与决定必须落在仓库文件中。

## 运行目录里的修改如何进入仓库

`patches/*.patch` 是相对于 `upstreams.json` 中固定提交的完整差异，不只是相对于最近一次本地提交。

- 修改 MaiBot 后，在其目录用 `git diff <固定提交> --相关文件` 检查差异。
- 插件使用自己的固定提交和补丁，不能在外层仓库混为一个 Git 基线。
- 导出补丁时用能保持 UTF-8 的方式，避免 Windows PowerShell 默认重定向编码改变补丁。
- 检查新文件：普通 git diff 不包含未跟踪文件，必须显式纳入导出流程。
- 身份占位值与密钥必须在发布副本脱敏，不能将已填真实账号的运行 diff 直接提交。
- 同步 `apply_response_guarantees.py` 对应函数。连续运行两次应该无额外改动，否则启动可能重新插入重复代码。
- 更新了上游版本就同时更新固定提交、补丁和验证记录，不能只改某一个。

队友已有定制时，先在隔离副本运行 `git apply --check`，再处理冲突；不直接跑 bootstrap 覆盖现有实例。配置采用人工比对，数据库和聊天数据不通过 Git 同步。

## 交接模板

```text
任务编号与目标：
分支与提交：
涉及文件及函数：
输入 → 处理 → 输出：
改了什么配置或数据：
验证命令、输入及结果：
尚未验证／已知问题：
接下来做什么：
是否需要重启（本次是否已重启）：
```
