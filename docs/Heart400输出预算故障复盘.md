# 面试复盘：短JSON为什么也会用完400的输出预算

2026-09-22复核。先前说明中的“疑似截断”需要更新：本次在原生日志找到了只由finish_reason=length触发的告警，已经确认失败请求发生了长度限制停止。仍不能确认旧请求究竟是思考、额外说明还是正文占满预算。

## 1. 一开始选400合理吗？

400可以是一个待验证的短输出实验起点，不是必然错误。只有四个字段、短原因和短原话，若模型直接返回JSON，几百token可能足够。为调用设限也是合理的成本与异常输出保护措施。

错误不在“任何时候都不能设400”，而在于把未经目标模型实测的经验值写死，误把预期最终JSON长度当成可以保障整个生成过程完成的预算。初版模拟测试直接给了完整JSON，验证了程序的解析/计分规则，没有验证实际模型会如何生成这份JSON。

不能为初始实现的设计意图编造精确概率或不存在的性能测量。更准确的判断是：

| 推测 | 可支持到什么程度 |
|---|---|
| 认为短评分JSON用400足够 | 与实现的短输出假设一致，但不是经实测保证 |
| 限成本、延迟和废话 | 是合理目标，但没有证据证明400是最优值；硬截断不是约束格式的可靠方式 |
| 未充分测试的经验值 | 初版没有目标模型端到端验证，只做模拟返回测试，属于真实验证缺口 |
| 后来字段增加而预算没跟上 | 缺少证据；初版已要求delta、confidence、reason、evidence四项，不能据此认定是后来扩需求造成 |
| 400与4096有某种特殊换算 | 代码不存在这种关系。一个是插件显式值，一个是任务配置；显式值优先 |

## 2. 代码证明：4096没有自动保护这次请求

原插件appraiser.py发送：

```python
await self.plugin.ctx.call_capability(
    "llm.generate", task_name="utils", max_tokens=400, ...
)
```

SDK转发参数；宿主src/plugin_runtime/capabilities/core.py构建请求时继续使用：

```python
max_tokens=args.get("max_tokens")
```

再往下，src/llm_models/utils_model.py的优先级关键片段是：

```python
if max_tokens is not None:
    return max_tokens
# 之后才依次考虑模型配置、extra_params、任务默认值
return self.model_for_task.max_tokens
```

因此，这次明确填写400，不会因为utils任务默认4096就自动变成4096，更不是400+4096或自动升级。当前OpenAI兼容客户端继续把解析后的值送给上游；它也支持特定模型的max_completion_tokens兼容分支，不能把所有API参数语义当成完全一样。

类比：酒店默认可住到12点，但你这张订单特别写明10点退房，系统按订单执行。这里4096是任务的配置值，不是模型的全部上下文容量。

## 3. 证据链

原生应用日志app_20260922_132929.log.jsonl中对应三次评估：

| 时间 | 长度警告 | 心情调用报告输出用量 | 插件结果 |
|---|---|---:|---|
| 13:37:58 | 有 | 400 | JSONDecodeError |
| 13:38:39 | 有 | 400 | JSONDecodeError，刺激0 |
| 13:40:57 | 有 | 400 | JSONDecodeError，刺激0 |

没有把包含QQ身份、私聊等信息的完整日志放进本包；这里只保留与故障有关的统计和结论。

原生日志告警的代码（src/llm_models/model_client/openai_client.py）为：

```python
if finish_reason == "length":
    logger.info("模型...因为超过最大 max_token 限制，可能仅输出部分内容，可视情况调整")
```

因此并非仅仅“400恰好相等所以猜测截断”：有明确的长度停止信号，与用满400、JSON解析失败在时间上对应。官方接口说明也指出length与输出/上下文长度限制相关，并提醒JSON模式仍可能被长度限制截断。[DeepSeek Chat Completions官方说明](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)

综合证据强烈支持：在这些请求中，400预算在形成可读取评分前耗尽。尚不能复原当时正文长什么样；不能把具体是“缺最后一个括号”还是“没有最终正文”说成亲眼看到。

## 4. 为什么JSON很短，生成过程却可能更长？

第一，要求返回简短JSON不等于模型一定遵守，可能生成解释、反复措辞，或在不合适的模式下继续输出。

第二，token不是汉字计数。JSON字段名、标点、中文原因和证据都会占用token，不能从“看着只有几十字”精确推算预算。

第三，部分推理模型会将思考过程计入输出预算。例如DeepSeek-R1官方更新明确说明max_tokens包含思考过程。它证明这种机制真实存在，但不能据此断言本次deepseek-flash调用一定以同样方式消耗了400；模型别名、服务配置和旧返回详情仍需核实。[DeepSeek官方更新说明](https://api-docs.deepseek.com/zh-cn/news/news250528/)

“不要输出思维链”是自然语言要求，不等于通过接口关闭思考模式。即使用户看不见思考内容，它在某些模型上仍可能影响预算、耗时和费用。我们不需要读取或保存隐藏推理才能观察预算和完成原因。

## 5. 一个特别重要的反例：修复后实际只用了163和153

之前授权的两次真实修复验证，原生用量日志app_20260922_212532.log.jsonl记录：

| 新版测试 | 预算 | 实际输出用量 | 可读评分 |
|---|---:|---:|---|
| 真诚感谢并关心 | 4096 | 163 | +2，置信度0.88 |
| 感谢陪伴聊天 | 4096 | 153 | +4，置信度0.95 |

这很重要：**4096不是每次一定生成4096，也不能据此说这项任务天然至少需要4096。**成功返回的两份结果本身甚至都少于400。

新版同时提高预算、给出明确JSON示例并增强完整对象解析；测试输入与上下文也没有做到严格一致。没有只改变一个变量的A/B对照，因此不能声称“成功全靠调大预算”，或把各项修复贡献量化。用户后续反馈实际聊天能正常改心情，说明工程方案可用，不代表完成了因果实验。

400可能够某些请求，却不能保障旧提示词/模型组合的尾部情况。更大的预算提供余量，明确格式降低跑偏概率，严格校验保障坏结果不会随便改变状态。

## 6. 为什么聊天能回复，但心情没变？

正常聊天和心情评估是两条不同的模型调用。聊天回答成功不代表评估成功。JSON解析失败后插件将本次刺激记为0，这是正确的保守策略，不应为了让演示“有变化”而猜一个分数。

旧版只保存JSONDecodeError类型，用户日志又归并成“返回无效或调用失败”，导致无法立即判断是上游调用失败、空正文还是格式失败。原生有length告警，但该信号没有作为独立字段传到插件的capability payload里，因此需要跨层检查。

## 7. 已做的改进与仍未做的事

已做：输出预算可配置4096；等待上限默认20秒；明确JSON示例；只接受完整且唯一的评分对象；检查数值/原话证据；记录正文长度、用量/预算和具体失败类型；增加倍率、正负上限；保留冷却/全局上限；当前共51项离线测试，此次预算故障修复还做过两次真实隔离测试。

仍未做：自动透传finish_reason/reasoning_tokens到插件、针对不同模型的系统化预算基准、严格单变量A/B、多样本误判率评估。不要把这些未来方向写成已完成功能。当前插件仅凭用量达到预算给出“疑似不完整”仍是合理的，因为未来每次调用不一定都有我们这次查到的原生日志证据。

若之后获准进一步实验，可固定模型/输入/提示词，对400、1024、2048、4096做多样本比较，同时记录有效JSON率、length比例、正文长度、实际输出用量、响应时间和每个有效结果的成本；只留元数据和简短判断理由，不存隐藏推理。本次没有新增收费模型实验。

## 8. 面试时可以怎样讲（约一分钟）

“我们给角色增加了AI情绪评估。初版认为只有四个JSON字段，就把输出预算设成400，但真实运行时心情没有变化。我们没有直接放宽状态校验，而是追踪独立评估调用，发现原生长度停止警告、输出用满400以及JSON解析失败。进一步发现插件显式参数覆盖了任务配置。我们将预算和变化强度做成可配置项，改进输出约束、解析和错误日志，并用隔离状态验证，避免测试污染真实记忆。修复后输出只用了153和163个token，所以我们不把4096说成理论最低值，也不把同时改了多个因素的结果当成单变量证明。这个过程让我们认识到：模型调用成功不等于业务结果有效，短答案也需要真实模型验证和跨层可观测性。”
