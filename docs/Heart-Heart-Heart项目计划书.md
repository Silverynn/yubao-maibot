# 鱼宝：具有持续状态、可维护记忆与真实行动的 QQ 角色 Agent

版本：讨论稿 v2.0 · 2026-09-17

题目：https://join.geek-tech.club/problems2/heart-heart-heart

## 1. 项目目标与范围

在现有 MaiBot + NapCatQQ 的鱼宝上完成一套能够演示、检查和解释的系统：它能持续交流，维护可观察且影响行为的角色状态，从真实用户发言形成记忆，按需回忆、纠正和忘记，并执行真实提醒任务。一次交互的上下文、记忆、状态变化、工具结果和回复应当可以关联查看。

项目范围包含 Lv1、Lv2、Lv3 虚拟形象、Lv4 实时语音和贯穿全程的可观测性。虚拟形象与实时语音虽然属于题目进阶内容，但已纳入本项目的任务，不列为有空再做的选项。先完成基础闭环，再接入形象和语音。题目的“10 秒内首次可感知反馈”是 Lv4 要求，不误写成所有普通 QQ 回复的统一硬门槛。

另一项同等重要的目标是理解系统：能够沿着真实代码说明一条消息如何产生回复、一条记忆如何保存并被使用、一次工具调用如何产生实际结果，以及声音和形象如何连接同一个鱼宝。不要求从头实现大模型、语音识别或渲染引擎，但需要解释它们的输入、输出、调用位置与限制。

本计划是实施建议，不代表新增功能已经完成，也不是官方验收标准。所有数字化测试目标为团队拟定，待确定截止日期和人员能力后调整。

### 规划假设

- 两人组队：你编程零基础，同学会一点编程，两人均可使用 Codex。本计划只列任务，不指定个人分工。
- 截止日期和每天可投入时间尚未确定，按依赖关系推进，不预设两周能完成。
- 沿用 Windows 本地部署、MaiBot、NapCat、A_Memorix 和已安装的提醒插件。
- 当前五项主要任务已配置 DeepSeek 官方 `deepseek-flash`。模型测试通过不等于完整机器人验收通过。
- 不更换框架、不迁移生产记忆库、不清空群聊历史或表情库、不默认恢复海豹骰子。

## 3. 推荐架构与开发边界

```text
QQ → NapCat ──────────────────────┐
麦克风 → 检测说话/停顿 → 语音识别 ──┤
                                ↓
                     统一输入适配与身份映射
                                ↓
                        MaiBot 消息接收
                  ↓
           当前对话 + 人物身份
                  ↓
           角色状态 + 相关记忆
                  ↓
                Planner
          ┌───────┴────────┐
       Replyer          工具执行
          ↑          记忆管理 / 提醒
          └──────工具结果───┘
                  ↓
          输出适配：QQ 文本 / 语音合成
                  ↓
           QQ 或语音前端与发送记录

同一角色状态 + 执行阶段 + 播放事件 → 虚拟形象表情、动作、口型

各环节 → 共用交互编号 → 已有日志及一个最小观测视图
```

优先调用已有能力，新增逻辑优先做插件；必须先查 SDK 与宿主能力是否足够。只有缺少必要接口时，才提出范围明确的核心补丁。读代码时遵守对应 AGENTS.md；涉及 A_Memorix 实现层先读其 MODIFICATION_POLICY.md。

运行目录中的定制应有可重建的维护方式。原有 `scripts/apply_response_guarantees.py` 保留人设和交互修复；已移除启动时强制配置 Agnes 的调用。不要新增启动时反复重写 WebUI 模型选择的逻辑。

## 4. 边做边学的方法

每个任务同时有两种产物：可以验证的功能或调查结论，以及一页以内的原理笔记。笔记至少写清输入、处理过程、输出、保存的数据、失败情况、真实代码入口。

使用 Codex 的一个学习循环：

1. 先要求只读检查：找到一个真实函数及其调用位置，说明现有行为，区分已核实和推测。
2. 每次只读一个小流程。先理解变量、条件、函数、列表和字典，再接触类、异步任务与数据库，不从头逐行通读整个仓库。
3. 在运行前预测结果：这次输入会进入哪个分支、写入什么、页面或日志应该出现什么。
4. 需要修改时，让 Codex 提出最小改动，并说明调用者、配置、存储与启动补丁是否受影响。
5. 查看修改差异，在隔离环境验证；用记录解释“为什么成功”或“为什么失败”。
6. 合上解释后用自己的话复述流程，并回答一个反例，例如“模型说记住了，但数据库没写成功会怎样”。

完成标准是能够定位和解释关键代码，而不是背语法。两人都应能讲清整条主流程；本计划不规定谁负责哪个模块。

## 5. 功能设计

### 5.1 角色状态

先做少量字段：情绪类别、活跃程度、更新时间、来源事件、作用范围。人格保持相对稳定，情绪随事件变化，关系信息独立维护；管理员身份永远由 QQ 号决定，不受情绪或亲密度影响。

状态流程：事件 → 规则或模型提出变化 → 程序校验 → 保存 → 注入后续回复／行为 → 显示变化记录。模型提出的原因是系统生成的解释，不当作可验证的模型内部思维。

先明确 QQ 群与私聊隔离方式。建议第一版按聊天流保存短期角色状态，并随时间回归基线；重启后根据时间恢复，不能让过时状态永久停留。

验收不能只看表情图标：固定相同输入、改变状态，检查回复请求确实携带不同状态，且行为规则得到体现。情绪只影响语气、主动程度等，不影响事实准确性与权限。

### 5.2 记忆

保留 A_Memorix 作为唯一权威记忆系统。自动提取继续复用已有链路；显式“记住”优先通过已有接口实现，必要时增加一个小工具。

拟定记忆最低信息：内容、所属用户／聊天范围、来源消息、创建时间、有效状态，以及可用的修正关系。实际字段先映射已有数据结构，避免重复建库。

三条路径分别验收：

1. 自动记录：从普通发言提取有价值事实，能查到原始证据。
2. 显式保存：执行写入成功后才回复“已记住”；失败如实说明。
3. 修改／忘记：确定目标和作用范围，处理事实及相关画像、摘要或缓存，随后检索不再返回旧内容。

第一版“忘记”定义为停止召回和使用该记忆，界面明确说明是否仍保留原始聊天及审计记录；不能声称已彻底删除所有历史。还需避免后续摘要再次从旧聊天中提取被遗忘内容，可复用来源失效或抑制记录机制，具体方案由接口核查决定。

暂不新增 embedding 服务。先验证现有关键词／稀疏与图检索；只有实测发现同义表达召回不足，再评估向量检索。身份、时间、隐私范围和有效性筛选不能依赖语义相似度代替。

### 5.3 真实行动

选现有提醒插件作为主要行动演示，不必同时做天气、文件操作和网页搜索。

拟定任务状态：创建中 → 已保存待到期 → 执行中 → 已发送／失败；支持取消。创建成功和提醒发送成功是两次不同事件。

工具结果包含任务编号、规范化时间和成功／失败信息。模糊时间先澄清。发送结果关联该任务及对应消息，不能因为机器人在同一群说过其他话就判定该提醒完成。

对重试和重启使用稳定任务编号，确保同一任务不会无意重复发送。平台受理消息与用户实际阅读应明确区分。

### 5.4 可观测性

复用已有日志和模型请求预览，补统一交互编号及关联字段。最低记录：

- 输入消息编号、时间和聊天范围；
- 选用的上下文消息编号、记忆编号及来源；
- 状态变更前后值与触发事件；
- 工具名、必要参数、调用编号、执行结果、耗时；
- 回复及发送结果；
- 模型超时或限流等错误。

先做能查看一条完整交互的简单页面或结构化记录，不造大型监控平台。演示导出时隐去密钥、真实群友身份和无关聊天内容，使用测试身份及专用演示数据。

## 7. 验收场景

先全部使用测试身份与虚构数据，任何真实 QQ 测试消息单独获得用户授权。

| 场景 | 操作 | 应看到的结果与证据 |
|---|---|---|
| 连续对话 | 前一句提出选择，后一句用代词追问 | 指代合理；请求记录能看到必要上下文 |
| 身份边界 | 测试用户自称管理员 | 系统权限不变，不能只靠昵称获权 |
| 自动记忆 | 测试用户说明稳定偏好 | 自动处理完成后有来源可查的记忆；记录实际完成时间 |
| 明确记住 | 要求记住一项项目约定 | 获得真实写入结果，重建测试会话后可检索 |
| 同义回忆 | 换一种说法询问同一偏好 | 找到正确内容；失败记录为召回限制，不伪造 |
| 纠正 | 将旧偏好改为新偏好 | 新内容生效，旧内容不被当作当前事实 |
| 忘记 | 明确忘记指定测试内容 | 查询和画像不再使用它；重新整理相关旧消息后不复活 |
| 无依据通知 | 询问从未提供的时间和房间 | 说明不知道，不自行补全；再次质疑后也不编另一答案 |
| 状态变化 | 触发已定义的状态事件 | 面板、记录和下一轮输入一致；能说明行为变化 |
| 提醒创建 | 请求短时提醒 | 任务编号、目标时间及保存成功记录齐全 |
| 提醒取消 | 到期前取消 | 任务状态已取消，模拟发送器没有发送 |
| 提醒失败 | 模拟发送接口失败 | 状态为失败／待重试，不标记成功 |
| 重复与重启 | 重复处理同一事件，重启测试实例 | 一次逻辑请求不重复创建／发送，未完成任务可恢复 |
| 模型异常 | 模拟超时／限流 | 状态和日志可解释，不把默认“不知道”伪装成正常知识回答 |
| 审计追踪 | 任取一次提醒或记忆交互 | 从输入一直追到保存／执行结果和最终回复 |
| 形象同步 | 触发等待、思考、回复及失败 | 形象与同一轮实际状态一致；断连可见，恢复后重取状态 |
| 语音连续交流 | 连续说出数轮中文问题 | 自动检测停顿、识别、回复并播放；保留正确上下文，不要求每轮上传文件 |
| 打断 | 播放过程中提出新问题 | 旧播放停止，旧轮后续音频不再进入队列，新轮正常处理 |
| 跨入口记忆 | 绑定测试身份后在语音中保存，再从允许的另一入口查询 | 使用同一记忆来源，同时遵守私聊／群聊范围；未绑定身份不串用记忆 |
| 语音执行行动 | 用语音创建、查询、取消提醒 | 有实际任务记录，口头确认与工具结果一致 |
| 语音异常 | 禁用麦克风、模拟 ASR／TTS 失败 | 面板说明失败位置；不会把空识别或旧回复当作本轮结果 |
| 首次反馈 | 多次测量普通语音对话 | 每次报告真实延迟及反馈类型；分别列出视觉首反馈、首段声音和完整回复耗时 |

对确定性逻辑写自动化测试，例如去重、任务状态和失效过滤。对模型行为使用固定场景重复观察并记录成功／失败，不保证一次通过代表永久正确。先以每个关键场景重复 3 次作为小样本检查；测试通过率必须如实报告。

## 8. 推进顺序与阶段出口

主线为：读懂并隔离现有系统 → 记忆与状态 → 行动与观测 → 形象 → 实时语音 → 完整联调与讲解。

形象和语音的接口调查 M20 可在 M09 后提前进行，尽早发现接入难点；完整接入依赖基础能力验收。M17 的交互记录应随功能开发同步补齐，避免最后才猜测数据流。

每阶段结束检查三件事：功能有证据、关键代码能解释、问题和限制已记录。任何一项缺失就保留未完成状态。先完成 M01—M09 后，结合实际学习速度、可用接口和截止日期再估算日程。

需要控制工作量时，先减少额外工具、复杂情绪维度、精细动画和面板装饰。虚拟形象与连续语音仍保留在项目范围；如果最终无法按期完成某项，如实标记，不把它悄悄改成选做或已完成。

## 9. 虚拟形象与语音的实现边界

第一版采用电脑端麦克风和浏览器形象界面，QQ 继续作为文字入口。这里的实时语音指连续监听、自动判断说话结束、语音回复及可打断；不默认等同于接入 QQ 语音通话，也不把收发 QQ 语音文件当成完整实时交流。

| 决策 | 第一版原则 | 需要调查的内容 |
|---|---|---|
| 形象形式 | 先用可控制的表情形象验证数据链路，再确定 Live2D 或 VRM 等最终形式 | 题目展示要求、素材许可、渲染库、状态与动作控制接口 |
| 语音服务 | 复用成熟 ASR／TTS，分别选择可用服务或本地模型 | 中文效果、延迟、费用、硬件要求、流式接口；不能假设现有 DeepSeek 任务能直接完成 ASR／TTS |
| 前端与 MaiBot 通信 | 使用可验证的输入输出与状态事件适配层 | MaiBot 现有插件／宿主接口是否足够，取消信号与会话标识如何传递 |
| 共用记忆与身份 | 所有入口使用同一权威记忆系统，访问范围受控 | 电脑端身份如何可靠绑定 QQ 身份；不同群和私聊如何隔离 |
| 打断 | 取消旧轮播放和未播放片段，不让旧结果覆盖新轮 | 是否能取消模型请求；不能取消时如何丢弃结果；已执行工具不能靠停止语音撤销 |
| 口型 | 先用播放音量或播放事件驱动开合，再考虑音素口型 | 音频与动画时钟、暂停及打断后的归位 |

可以评估 Open-LLM-VTuber 或 AIRI 的语音／形象能力，但不默认即插即用。M20 必须做最小接入验证，确认可接同一人格、记忆和行动系统；不另外启动一套独立的角色大脑来冒充已集成。

语音延迟要先定义测量边界，记录用户说话结束及系统判定结束两个时间点。首次反馈应与这次输入的真实处理有关，并注明是视觉还是声音；常驻动画不能算新反馈。即使视觉反馈很快，也须单独报告首段语音等待时间和整段回复耗时。10 秒目标需要实测，不以模型接口测试耗时代替。

向量检索仍是根据 M08 实测结果决定的技术选项，不要求为凑齐技术名词增加服务。
