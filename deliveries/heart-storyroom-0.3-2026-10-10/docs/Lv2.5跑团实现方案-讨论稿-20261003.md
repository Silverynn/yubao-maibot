定位：你和同伴担任主持人，两个 MaiBot 担任玩家角色，在同一个有限故事中行动。本文说明准备使用的工具、具体流程与效果；“计划增加”不代表已经完成。

## 1. 总体做法：自建共享主持台，连接现有机器人

采用 **StoryRoom 网页平台＋两台 MaiBot 的 PC 连接插件＋双 Live2D 舞台**。

StoryRoom 是我们已经制作了本机原型的独立平台，不是第三方现成跑团网站。房间就在它的网页中创建，不需要在 QQ 或 MaiBot WebUI 中建房。

```text
你的 MaiBot ──PC连接插件──┐
                          ├── StoryRoom：房间、剧情、骰子、裁决、记录
同伴 MaiBot ──PC连接插件──┘                    │
                                             ▼
                              主持人网页＋同场景的两个Live2D
```

MaiBot 负责角色的语言与行动提案；平台负责真实状态和流程；你们决定提案能否成立。原来的个人 Open-LLM-VTuber 聊天界面继续保留，跑团使用新的共享舞台。

### 使用的工具

| 工具 | 具体用途 |
| --- | --- |
| Python＋FastAPI | 编写 StoryRoom 后台，提供建房、领取任务、交提案和裁决接口 |
| MaiBot SDK | 编写 PC 连接插件，使用各自机器人已配置的模型 |
| SQLite | 保存房间、事件、角色状态和任务，重启后继续 |
| JSON 剧本配置 | 保存世界背景、阶段、允许分支、条件和结局 |
| PixiJS＋pixi-live2d-display | 在同一个浏览器画布显示两个模型，播放实际表情和动作 |
| 文生图工具；可选 ComfyUI | 制作场景背景；第一版手动生成、导入，不要求训练模型 |
| 云服务器＋Caddy（异地部署建议） | 提供双方可访问的 HTTPS 网页和接口；先本机验证，再决定是否部署 |

## 2. 房间在哪里创建，两台电脑怎样加入

### 本机原型的实际入口

项目位于 `//（我已隐藏我的文件地址）`。双击 `start.cmd`，浏览器打开 `http://127.0.0.1:8790/`。

登录密钥在项目的 `.runtime/主持人登录密钥.txt`，复制到 StoryRoom 登录框即可；它不是 MaiBot 管理员 token，也不是模型 API 密钥。

主持人登录后，点击“新建世界线”，填写房间名、两个角色名字，选择各自的 Live2D 模型。创建后取得两个不同的玩家连接密钥，每台机器人只使用自己的密钥。

一个房间就是一局独立故事，保存当前阶段、已确认事实、角色状态与操作记录。重启继续原局；新建房间才是新开局；进入结局后不自动续写新主线。

当前建房界面默认使用灯塔样例剧本。计划补上“选择剧本、角色卡、背景预览”等配置，不能假定这些界面现在已经存在。

### 两个 MaiBot 如何加入

1. 在各自 MaiBot 安装默认关闭的 `storyroom_pc` 插件。
2. 在 MaiBot WebUI 的插件配置填写：平台地址、自己的玩家密钥、角色设定、所用模型。
3. 启用插件。它定时检查自己的任务，有任务才调用模型，没有任务不请求模型。
4. 主持人在 StoryRoom 点“请某角色行动”，插件领取问题并回传发言、行动提案和情绪。
5. 同伴用同样方式连接，但使用另一把密钥和她自己的模型服务。

平台不需要两人的模型 API 密钥，也不自动读取私人 QQ 数据库。

### 异地怎么访问

推荐正式联调时，将同一个 StoryRoom 部署在一台可信的云服务器上，两位主持人的浏览器、两个 PC 插件都访问同一个 HTTPS 地址。两个 MaiBot 仍留在各自电脑运行，不必一起搬上服务器。

Caddy 负责将外部请求转给 StoryRoom，并在域名、证书验证和网络条件满足时提供 HTTPS；部署还需核对代理后的登录、同源校验和模型资源访问。[Caddy 官方说明](https://caddyserver.com/docs/automatic-https)

如果暂时不想购买服务器，也可讨论“主持人电脑＋受控 HTTPS 转发”的临时方案，电脑需保持运行。具体服务与费用待双方选择；本方案不自动购买或部署。

`127.0.0.1` 只能访问本机，不能直接发给异地同伴。第一版平台只用单服务进程，并顺序裁决，先不做多实例部署或完整同时回合。

## 3. 剧本与规则怎么做

### 剧本不是每句台词，而是有限的故事地图

先由你们定世界和主线，也可以让 LLM 辅助拟草稿，但最终由主持人审核、锁定。每个剧本至少包括：

| 内容 | 示例 |
| --- | --- |
| 世界边界 | 现代海边小镇，没有魔法和穿越 |
| 角色过去 | 两位探索者为何来到港口，之前有什么共同经历 |
| 开局和目标 | 暴雨夜灯塔熄灭，帮助渔船安全入港 |
| 阶段与地点 | 码头、机械师小屋、灯塔 |
| 关键事实 | 是否找到齿轮、清理镜片、完成预警 |
| 分支条件 | 齿轮与镜片准备完成，才可进入点亮灯塔结局 |
| 结局 | 修复成功、替代预警、未及时完成 |
| 角色变化 | 哪些经历改变信任、当前看法和情绪 |

先画阶段图，再按现有 `stories/lighthouse.json` 格式填写：`world` 写世界，`nodes` 写阶段，`next` 写允许去哪里，`requires` 写条件，`ending` 标记结局。

```text
码头 → 小屋搜寻 → 灯塔
                   ├─ 齿轮＋清理镜片 → 修复成功
                   ├─ 手持灯预警     → 替代结局
                   └─ 未及时完成     → 未修复结局
```

角色可以提出新办法，只要仍属于这条故事；不能凭一句话增加异世界或改写其他角色。程序检查阶段与条件，主持人审查自然语言提案。正式开局时应保存剧本版本，避免中途改文件改变旧存档含义；版本锁定是待补功能。

### 第一版规则建议：轻量 d20

规则尚未最终确定，建议先用以下可玩的简化规则，不宣称实现完整 D&D 或 CoC：

- 角色卡包括姓名、背景、目标，以及“调查、动手、交涉”三项技能。
- 技能加值先限定为 0～3，由主持人确定，避免模型随意加数。
- 判定公式：`1d20＋技能加值 ≥ 难度` 则检定成功。
- 示例难度：普通 10、较难 12、困难 15；主持人在投骰前确定。
- 第一版不额外设置 1 点／20 点自动失败／成功，减少规则歧义。
- 不需要冒险或不确定性的普通行为，可由主持人直接批准，不必句句投骰。
- 失败改变行动结果或路线，不强迫反复投到成功；重投需主持人说明原因。

例如“调查抽屉”使用调查 +2，难度 12；平台实际掷出 9，最终 11，检定失败。主持人可以确认“没有找到，但发现抽屉卡住”，让角色选择撬开、寻求帮助或换路线。

平台已有实际骰子，当前可人工填 `1d20+2` 和难度。角色卡界面、自动技能加值、检定绑定任务和重投限制需要新增。以后改用其他规则时，主要替换检定模块，不必重做房间与舞台。

## 4. AI 背景怎么生成、放到共同场景里

背景由 AI 制作，但不让它决定故事是否进入新世界。

### 工具选择

第一版用你们已有的文生图工具生成 PNG/JPG，再人工导入平台，避免额外部署图像服务拖慢进度。

若希望采用开源本地方案，可选 ComfyUI；它提供图像生成工作流和服务接口。后续可以由 StoryRoom 提交生成任务、取得候选图片，但本地生成所需模型和硬件要另行确认，不要求跑团服务器承担 GPU 推理。[ComfyUI 官方项目](https://github.com/Comfy-Org/ComfyUI)、[接口文档](https://docs.comfy.org/development/comfyui-server/comms_routes)

### 实际制作流程

1. 根据剧本列场景清单，例如“暴雨码头、机械师小屋、旧灯塔内部”。
2. 统一风格和比例：建议 16:9 横图，同一画风；给前景两个角色留位置。
3. 各场景生成几张候选。ai提示词可写：“现代海边小镇，暴雨夜，旧灯塔内部，暖色工作灯，无人物，无文字，无魔法元素，前景留空。”
4. 主持人检查是否符合世界、是否遮挡角色、是否含错误文字或不合理物体；不合格就重生成或精修。
5. 将批准图片导入 StoryRoom，绑定阶段，例如“灯塔 → tower.png”。
6. 主持人推进到该阶段时，网页切换背景，两个 Live2D 继续显示在同一画布前景。

图片只是视觉素材。图里偶然出现一扇门，不代表故事自动新增可进入的地点；可互动对象仍以剧本和主持人裁决为准。

计划增加“上传／预览／替换背景、绑定阶段”的界面。当前原型只有 CSS 背景，尚无 AI 生成或图片上传功能。第一步可先人工放入图片并绑定场景，自动调用图像模型以后再做。

## 5. 一轮游戏怎样运行

```text
主持人发布现场、点名角色
        ↓
PC读取角色设定、当前阶段与相关经历
        ↓
调用各自模型，返回发言＋行动提案＋情绪
        ↓
需要时由平台实际投骰
        ↓
主持人通过／退回，确认具体后果
        ↓
保存事实与经历，更新关系、心情、阶段及舞台
```

模型只提出“我想搜寻齿轮”，不能自行宣布骰点或成功。主持人确认后，“找到齿轮”才成为有效事实并影响分支。

第一版顺序点名，避免角色互相抢话。两位 PC 可以讨论同一问题，但现场一旦变更，另一份依据旧现场生成的提案要重新生成；以后若需要同时行动，再增加整轮统一裁决。

建议指定一位主主持人保存最终裁决，另一位参与叙事。当前只有统一主持人身份，两个独立账号及权限划分需补做。

## 6. 如何衔接记忆、心情和两个 Live2D

### 记忆：把跑团经历变成角色的过去

//lch的注解：我觉得这个记忆应该独立于原先的记忆库，以下内容为GPT想法不代表最终方案

只将主持人确认的事件写为角色经历，未裁决或未批准的提案不当作已发生事实。确认过的失败尝试也可以记住，例如“上次没能打开抽屉”；没达成目标不等于这段经历不存在。

后续模型获得：固定背景、当前阶段、已确认的关键事实、阶段回顾，以及与本次行动相关的经历。例如再次调查时记起“同伴此前帮我辨认零件”，从而影响选择和表达。

关系先用简化信任值记录变化，并让阶段看法进入角色提示词；暂不做完整关系图，也不凭一次投骰永久改掉角色人格。

故事记忆按“房间＋角色”隔离，先保存在 StoryRoom。再通过适配器与现有记忆插件衔接，默认不读写真实 QQ 私聊事实，也不覆盖原人物画像。必要时提供明确标注“跑团经历”的日常回顾入口。

修改剧情时，世界事实、分支条件和派生回忆一起修正；重复事件不重复写入。日志列出实际提供了哪些参考、新增或修正了哪些经历。

### 心情：复用逻辑，不直接覆盖同伴插件

通过通用状态接口对接双方心情插件，按“房间＋角色”保存心情值和临时情绪。

LLM 理解事件并建议情绪及变化原因；插件校验、限幅、保存，影响后续回复风格；舞台显示结果。可以合并到角色本次模型输出，减少额外请求，但裁决成功后的情绪要等真实结果产生，不能提前奖励尚未成功的行动。

“心情 80＋疑惑”可以同时存在。话题／事件结束时清理临时情绪并记录；某位观众刷新网页，不清空整个共享房间的状态。新局是否继承心情由开局设置决定。

### Live2D：共同网页绘制，不传视频

平台准备两套获许可的模型文件；浏览器在一个画布中分别加载。各自的表情状态来自 PC／心情接口，不是两台电脑传录屏。

计划完善资源自动识别：扫描模型实际的表情和动作文件，再由配置把“开心、疑惑、生气”等映射到具体资源。文件名不能证明情绪含义，因此保留人工校正；没有某表情时明确降级。当前原型主要读取已有 VTuber 映射，完整扫描和映射编辑界面仍需补做。

心情数值面板属于平台，不绑定具体形象。保留自动情绪控制及手动展示；计划提供舞台表情测试和中文列表，手动展示结束后恢复最新自动状态，不修改心情值。个人 VTuber 的指令不会自动出现在新平台里，需要接入实现。

## 7. 日志与最终效果

### 计划的日志形式

每个房间按天保存独立文件，同一行动合为一张卡片，先显示“处理中”，后续补齐：

- 时间、人物、主持人问题、角色回答和提案。
- 提供的记忆、新增／修正的经历。
- 实际骰点、加值、难度、主持人裁决。
- 心情变化、临时情绪产生／消失及原因。
- 表情请求、实际映射、启动成功／失败。
- 世界阶段与关键事实变化、模型错误和超时。

表情启动成功不写成“动画完整播放完毕”。完整故事日志先保留，不沿用日常聊天的三天自动清理，以便复盘和面试展示。

### 完成后的演示效果

主持人切到 AI 制作的“小屋”背景，点名月铃。月铃提出搜寻零件，显示“心情 80｜疑惑”，另一个角色在同一舞台倾听。

平台投骰并由主持人确认找到齿轮。下一次回应时，角色根据真实结果表现开心，保存共同经历。进入灯塔后换背景；两人继续合作，最终依条件进入某个结局。

中途关机后能继续原局；日志可以追溯“谁提议、骰点多少、谁批准、记住什么、为什么换表情”。这就是有限世界线、持续状态和 Lv3 联动的可展示闭环。

## 8. 当前基础与实施顺序

| 已有本机原型 | 仍要补齐或真实验证 |
| --- | --- |
| 建房、角色密钥、主持台与 PC 连接器代码 | 两个真实 MaiBot 及异地 HTTPS 联通 |
| 灯塔剧本、分支、投骰、提案与裁决 | 剧本选择／版本锁定、角色卡和正式检定绑定 |
| SQLite 保存与按房间／日期日志 | 长期经历检索、记忆／心情桥接、聚合卡片 |
| 两个 Live2D 同台及展示情绪 | 同伴真实形象、心情值面板、手动控制 |
| CSS 场景 | AI 图片导入、审核预览与阶段绑定 |

此前原型通过 49 项自动化测试，但不能代替真实模型、两台电脑和同伴形象的集成验收。

实施顺序：**定剧本与规则 → 补图片导入和角色卡 → 验证一个真实 PC → 双端异地联调 → 接记忆与心情 → 完整演示与日志验收。**

你们讨论时优先确定四件事：是否采用轻量 d20；使用什么原创剧本；共同平台的部署方式；跑团经历与日常角色记忆的关联范围。
