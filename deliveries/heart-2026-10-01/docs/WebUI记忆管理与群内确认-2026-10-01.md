# WebUI 记忆管理与群内确认（Heart 1.4.0）

## 一、先分清三个地方

首页的“表达方式审核”决定机器人怎么说话，不审核用户事实。

记忆管理页中的“候选与群回忆”是新增入口：审核 Heart 候选，直接修改原生正式群记忆。

“记忆查询、人物画像、记忆检修、纠错历史、删除”等是原生入口，继续保留。插件审核通过的正式内容也进入同一原生库，不复制出第二套正式记忆。Heart 独立保存的只是候选、待确认请求和审计记录。

## 二、怎样打开新页面

完整安装并重启 MaiBot 后，打开原来的 WebUI 管理地址，用原来的身份登录。

进入记忆管理页面，点击 **候选与群回忆** 标签。页面路由是 `/resource/knowledge-base?tab=heart`。

如果仍显示旧页面，按 Ctrl+F5 刷新。安装器会部署本地构建并写入专用标记，普通启动方式也会优先加载新前端。如果启动环境明确设置 `MAIBOT_WEBUI_USE_LOCAL_DASHBOARD=0`，它仍会加载原打包前端，需要移除此设置或改为 `1`；不用修改 bot_config.toml。

## 三、如何审查不确定的记忆

1. “群聊范围”选择一个群；选择“全部会话候选”可以管理所有候选，也包含私聊。全局后台内容不应截图公开到群里。
2. “候选状态”选 **待审核**，点击刷新。
3. 阅读拟记住的内容、人物、所属会话、暂存原因；展开 **查看原始发言证据**。
4. 内容准确，点击 **批准原文**。只有原生服务确认存储成功，页面才会显示已写入。
5. 提取的措辞不准确，点击 **编辑后批准**，修改文本后明确批准。不能在此更换群归属或人物身份，也不要将自己的猜测写成别人确认过的事实。
6. 不值得记住或证据不足，点击 **拒绝收录**。这只拒绝候选，不删除已有长期记忆。

批准后的内容经过原生存储及重复、冲突检查。如果发现冲突，状态变成 **冲突待本人确认**，不是“已经写入”；管理员批准不会自动覆盖旧事实。

审核结果可以切换“候选状态”查看。旧版候选可能没有详细暂存原因或原文快照，但写入时仍会核实原始消息。原始证据无法核实、模型核查失败时，不会因为点击批准就宣称成功。

“确定的事实自动写入”原有设置继续有效。要让所有自动人物事实先经过候选区，在插件设置的 **自动记忆与候选区** 中关闭 **核实后自动写入长期记忆**。群聊摘要仍由原生系统按消息窗口自动生成，并不是所有摘要都要逐条候选审核。

## 四、群里有冲突时怎样确认

### 候选筛选与删除

“候选状态”只筛选上面的候选／审核记录；下方“本群正式回忆”只随所选群变化，不随候选状态变化。标题显示当前筛选状态及记录数量。

每条候选／审核记录有“删除候选／审核记录”按钮，须在弹窗中再次确认。删除会记入日志，但不会删除已经写入原生库的长期记忆。要删除正式记忆，请使用原生“删除”页面。正在等待冲突确认的记录须先取消或完成确认，不能直接删除。

删除候选不是永久禁止机器人再次记住该话题；以后出现新的原始发言，仍可能形成新的候选。

机器人会在产生冲突的原群展示这个群原本可见的新旧内容，要求原发言者确认。

例如：旧事实“我喜欢围棋”，新事实“我现在不喜欢围棋了”。提示中会给出编号：

```text
/确认记忆更新 12
/取消记忆更新 12
```

必须由原发言者在收到追问的会话里发送。别人代答、换群确认、重复确认都不会再次执行。超过设定有效期不更新。私聊中产生的冲突继续在私聊处理。

这里保留明确编号，是为了在多个人同时聊天时知道用户到底在确认哪一件事。不把一句没有编号的“是”自动当成所有待办的确认。

为兼容升级前已经发出的私聊追问，那些旧请求仍需要在原私聊中确认；新产生的群冲突才在原群确认。

## 五、如何在后台修改已经存下来的群回忆

1. 选择一个群，查看下面的 **本群正式回忆**。它读取原生库，显示最近50条有效的本群人物事实及摘要。
2. 找到错误内容，点击 **修改原生记忆**。
3. 输入正确内容和修改原因，点击 **预览新旧内容**。这一步只生成修正计划，不修改正式记忆，也不调用 LLM 猜测你要改哪条。
4. 再次核对，点击 **确认修改原生记忆**。
5. 成功后，新文本进入原生长期记忆；旧文本由原生修正器标记过时，不再作为有效群回忆返回。相关人物事实证据和画像由原生流程维护，关联情景记忆重建会进入后台队列。
6. 回 QQ 发送 `/群回忆` 或 `/群回忆 关键词`，检查后续结果。更大范围查看仍可使用原生“记忆查询”。

这不是修改一份日志或修改画像的显示文字，而是执行原生记忆修正。旧内容保留审计历史，并非物理抹除。

预览10分钟后失效。期间若旧记忆被别人修改、撤回，或者新正文已经存在，系统拒绝按过期预览覆盖，请刷新。相同正文的合并请用原生记忆检修，不在此自动覆盖其他群或人物的记录。

修改不是原子的单个数据库事务。系统先核实新内容成功保存，再执行旧内容失效；如果部分步骤失败，可能新旧内容暂时都存在，页面和日志会明确提示，不会自动反复执行。请查看原生纠错历史核对。

## 六、原生页面分别适合做什么

| 页面 | 用途 |
| --- | --- |
| 候选与群回忆 | 审核不确定候选、精确修改某一群的正式回忆 |
| 记忆查询 | 查看原生权威记录、证据和关联内容，管理结构化事实 |
| 人物画像 | 查看人物介绍卡及证据、手动刷新、维护别名或手工覆盖 |
| 记忆检修 | 描述复杂修正需求，先检查计划和范围，再执行 |
| 纠错历史 | 查看原生修正计划及其执行记录；需要时使用原生提供的回滚 |
| 删除 | 预览、执行长期记忆删除，管理删除历史；不等于删除最近聊天上下文 |
| 图谱／情景记忆 | 查看从原生记忆派生的关系和经历；刷新可能需要后台任务 |

人物画像是整理出的介绍卡，修改“画像覆盖文字”不应当作批准了候选，也不一定改掉底层证据。纠正某条错误的群事实，推荐使用新增群回忆编辑入口。

已经送入某次模型请求的旧上下文，不会因后台编辑而倒退重写；后台维护影响后续检索。情景记忆重建、人物画像刷新可能需要等待，失败应查看原生日志和任务状态。

## 七、在哪里看日志

运行目录中的 `data/heart_observation/logs/QQ/` 按日期和会话分文件，Live2D 仍放在独立文件夹。搜索这些中文标题：

- **候选记忆**：暂存、管理员批准／拒绝、进入冲突确认、写入是否完成。
- **记忆冲突确认**：群内追问、本人确认、取消、过期、执行结果。
- **后台记忆管理**：修改前后正文、操作原因及管理员身份、预览或执行状态。
- **记忆操作结果**：原生服务实际写入／检索的内容。
- **群聊记忆检索**：`/群回忆` 实际返回了哪些内容。

管理员操作会明确标注“不等于用户本人确认”。原生存储中的 `manual_confirmed` 是“人工确认”这一兼容字段；管理员操作另有 `heart_review.confirmed_by=administrator` 或 `changed_by=heart.webui_admin`，不冒充用户本人。

## 八、测试与部署说明

本轮增加后台回归和页面交互测试，并检查 TypeScript 编译。测试使用虚构人物及隔离 SQLite，实际调用原生修正执行器；模型、向量出口和QQ发送使用模拟，不消耗真实模型额度，不修改现有记忆。最终测试数量以交付回执为准。

更新文件包含共享候选和冲突逻辑、宿主适配器、WebUI API和前端，不是只复制 plugin.py 就能使用。未修改 A_memorix 内核实现，也未改运行版主配置和密钥。

前端构建成功后，关闭 MaiBot，运行暂存根目录的 `安装记忆后台升级.ps1`。脚本备份被替换的文件和旧前端，不复制暂存配置、测试数据库、聊天或模型密钥。安装前端与后端必须配套，不能只替换一边。

完整部署完成前，新页面还不可用。请以安装完成回执及重启后的页面为准。
